# GitHub 이슈 운영

GitHub Issues를 작업과 논의의 단일 원본으로 사용한다. 코드 변경은 이슈, 브랜치,
PR 순서로 추적하며 Git 컨벤션은 [`docs/CONVENTIONS.md`](../CONVENTIONS.md)를
따른다.

## 이슈 작성

- 기능, 개선, 문서 작업은 `작업` 폼을 사용한다.
- 재현 가능한 오동작은 `버그` 폼을 사용한다.
- 한 이슈는 한 사람이 한 PR에서 완료할 수 있는 범위를 기본으로 한다.
- 큰 작업은 상위 이슈와 sub-issues로 나눈다.
- API 키, 개인정보, 원문 데이터 등 민감정보를 본문과 첨부 파일에 넣지 않는다.

## 라벨

| 라벨 | 적용 기준 |
|---|---|
| `bug` | 기대 동작과 다른 재현 가능한 오동작 |
| `feature` | 새로운 기능 또는 사용자 가치 |
| `docs` | 문서 작성과 수정이 결과물인 작업 |
| `chore` | 저장소, CI, 개발환경 정비 |
| `urgent` | 서비스 중단, 시크릿 노출, 실격 위험 등 즉시 확인할 문제 |
| `blocked` | 선행 작업이나 외부 결정 없이는 진행할 수 없음 |

이슈에는 `bug`, `feature`, `docs`, `chore` 중 하나를 적용한다. `urgent`와
`blocked`는 필요한 경우에만 추가한다. 버그 폼은 `bug`를 자동으로 적용하고,
작업 폼은 선택한 작업 종류에 맞는 라벨을 이슈 생성 후 적용한다.

## 진행 상태

별도 상태 라벨은 사용하지 않는다.

- 열린 이슈: 아직 완료되지 않은 작업
- 담당자 지정: 작업 중
- 연결된 열린 PR: 리뷰 중
- 닫힌 이슈: 완료하거나 더 진행하지 않는 작업

진행을 막는 문제가 생기면 `blocked`를 붙이고 이유를 댓글로 남긴다. 문제가
해결되면 라벨을 제거한다.

## 브랜치와 PR 연결

실제 이슈가 있는 브랜치는 `<type>/<issue-number>-<short-description>` 형식을
사용한다. PR의 `관련 이슈`에 번호를 적고, 병합으로 이슈가 완료될 때만
`Closes #번호`를 사용한다. 이슈가 계속 열려야 하면 `Refs #번호`를 사용한다.

PR에는 구현 결과와 실행한 검증을 기록한다. CI 통과만으로 완료 조건을 대신하지
않으며, 이슈에 정의한 완료 조건을 리뷰에서 확인한다.

## 운영 점검

- 작업을 시작할 때 담당자를 지정한다.
- `urgent`와 `blocked` 이슈를 우선 확인한다.
- 오래 담당자만 지정된 이슈와 리뷰가 멈춘 PR을 주기적으로 확인한다.
- 신규 기능, 리팩터링과 버그 수정은 날짜 기반 Phase가 아니라 이슈의 우선순위와
  PR별 안정성 검증을 기준으로 진행한다.
