## 2026-08-15 청킹 전 Normalization layer 필요성 A/B

- 가설: DoclingDocument(raw dict)를 chunker가 직접 순회하는 것보다, 얇은
  NormalizedDocument(heading/text/table/faq 블록 + page/level)로 변환 후
  chunker가 그 블록만 소비하는 편이 코드 복잡도·문서유형 확장성 면에서 낫다.
- 방법: `experiments/chunking-ab/`에 최소 prototype 작성 (production 코드 미변경,
  embedding/Qdrant 미구현). 샘플 4건(doc55/doc29/KR5113420013/doc56 NAVER OCR)에
  대해 variant A(DoclingDocument 직접 순회)와 variant B(정규화 후 순회)가 동일한
  청크를 만드는지 확인하고, `run_ab.py`가 LOC/문서유형분기 수/Docling 스키마
  식별자 수를 소스에서 직접 세어 표로 뽑는다. doc55는 기존
  `pension_agent.ingest.heading_recovery.recover_doc55_heading_hierarchy`를
  그대로 재사용(읽기 전용)해 두 variant가 공통으로 쓰는 마크다운 경로로 처리.
- 결과: (수치 — `python experiments/chunking-ab/run_ab.py` 실행 결과)
  - 4개 샘플 전부 A/B 청크 결과 완전 일치 (assert 통과).
  - LOC: A의 청커(variant_a.py) 48줄(스키마 탐색+분기+정책 진입점이 한 파일에 혼재).
    B는 정규화 계층(normalize_b.py) 48줄 + 청커 본체(variant_b.py) 6줄로 분리.
    청킹 정책(chunk_core.py, 양쪽 동일 사용) 72줄은 공통.
  - Docling 스키마 식별자($ref/self_ref/table_cells/prov/children/groups/bbox)
    참조 수: A의 청커 11회, B의 청커(variant_b.py) 0회 — B는 청커에서
    Docling 스키마 의존성이 완전히 격리된다.
  - 문서유형별 분기 수(`# doc-type-branch` 표시 기준): A=3, B의 정규화 계층=3,
    B의 청커=0. **정규화가 분기 자체를 없애주지는 않는다 — 위치만 정규화
    계층으로 옮긴다.**
  - metadata/page/table 보존: A/B 사이에 차이 없음(같은 walk 로직을 공유하므로
    당연). doc55만 heading_recovery의 마크다운 경로를 타서 page=0(정보 없음) —
    이건 A/B 공통 한계이며 normalization 도입 여부와 무관.
  - 중복 로직: variant_a.py와 normalize_b.py 텍스트 유사도 82% (실험 안에서는
    사실상 같은 walk 코드가 두 벌 존재 — 실제로는 A/B 중 하나만 구현하므로
    운영에서는 발생하지 않는 실험 특유의 중복).
- 결론: **KEEP_NORMALIZATION** (보류 아님, 채택 방향으로 판단하되 이번 PR에서
  운영 코드에 반영하지 않음 — 요청 범위가 실험까지였음).
  - 근거: (1) `PROJECT_RULES.md`가 `retrieved_context` precision 평가와
    근거 문서 표시를 요구한다 — page/heading 메타데이터를 청킹 이외의 소비자
    (agent의 근거 인용, evals)에서도 재사용할 가능성이 높고, 이는 정규화
    계층이 이미 제공하는 안정적 산출물이다. (2) 문서 유형이 이미 10종
    검증되었고 앞으로 늘어날 여지가 있는데(`docs/operations/document-parsing.md`
    문서유형별 채택 정책), B는 새 유형 추가 시 변경 범위를 정규화 계층
    한 파일로 제한한다 — chunk_core/청커 본체는 건드리지 않는다. (3) Docling
    스키마 의존성이 청커에서 0으로 격리되어, 향후 Docling 버전/파싱 프로필이
    바뀌어도 청킹 정책 코드는 영향받지 않는다.
  - 단서: 문서유형별 분기 수 자체는 줄어들지 않으므로(3=3), "normalization이
    분기를 없애준다"는 과장된 기대는 하지 않는다. 실제 도입 시 스키마 대신
    얇게 유지(4종 블록 그대로) — 이번 실험 이상의 class/schema 설계는 불필요.
- 관련 PR/이슈: 없음 (prototype만, 미커밋).

## 2026-08-17 투자설명서 hierarchy recovery + 92개 chunk validation

- 가설: raw Docling JSON 단계(정규화 계층)에서 marker/orig/document
  order/page provenance만으로 "제N부 → N. 항목 → 가/나/다" 3단 계층을
  파일명·운용사 하드코딩 없이 일반화해 복원할 수 있고, chunker는 그 결과
  (`NormalizedBlock.level`)만 신뢰하면 Docling label/marker/orig를 몰라도 된다.
- 방법: `data/raw/prospectus` 100개 원본을 SHA-256 기준 92개 unique content로
  정리 → 전량 Docling local-ocr-v1 파싱(실패 0) → `pension_agent/ingest/normalize.py`
  에 pictures.children 재귀(본문 텍스트가 picture 자식에 붙는 corpus-wide 구조
  대응) + marker/orig 기반 hierarchy 복원(표지/목차 echo는 document order + 1→5
  monotonic sequence로 배제, 합쳐진 부모/자식 노드는 문자열 내 모든 패턴
  occurrence로 분리) 구현 → `pension_agent/retrieval/chunker.py`는 자체 정규식
  재판정(`_COVER_PART_ECHO`/`_prospectus_heading_level` 등)을 전부 제거하고
  `block.level`만 신뢰하도록 축소 → 대표 5개 문서 chunk QA에서 "제1부 진입 전
  법정 유의사항도 N. 번호를 써서 level2 heading으로 오승격되는" corpus-wide
  false positive를 발견 → `normalize.py`에 state 플래그(실제 제1~5부 진입
  여부) 추가해 본문 진입 전 승격을 차단(내용은 text로 보존) → 92개 unique
  전체에 대해 normalize+chunk를 실행해 자동 validation.
- 결과: (수치 — `experiments/prospectus-full-chunk-validation/validate.py` 실행 결과, 미커밋 조사 스크립트)

    법정 유의사항이 heading으로 오승격돼 이후 17개 chunk의 section_path를

## 2026-09-05 복수 상품 비교 도구의 HCX 실경로 검증

- 가설: 복수 상품을 하나의 식별 계획으로 받고 상품별 병렬 검색과 비교 셀 제출을 연결하면
  기존 단일 Query 경로의 복수 Tool 응답 오류를 피하고 근거를 보존할 수 있다.
- 방법: 별도 worktree에서 HCX-007 비추론·기존 Qdrant를 사용하는 실제 `GET /answer` 경로에
  3개 채권형 상품의 차이와 안정성을 묻는 질문을 적용했다. 개발 중 수정판을 포함해 API
  진단을 7회 수행하고, 실제 검색 결과를 재사용한 HCX 제출 단계도 별도로 1회 재생했다.
  개인 질문 원문·실행 원문·추적 링크는 로컬 제외 경로에만 보존했다. 서로 다른 수정판을
  포함하므로 7회를 동일 버전의 성공률 표본으로 집계하지 않는다.
- 결과:
  - 최종 구현의 lint·format·mypy 통과, 테스트 1,205개 통과·1개 skip, 패키지 빌드 통과.
  - 최종 API 진단에서 최초 오선택된 1개 코드를 제한된 Planner 교정 1회로 수정했고,
    3개 상품을 정확히 식별했다. 문서 범위가 분리된 검색 3회는 약 0.753초에 완료됐다.
  - API 총 지연은 79.129초였다. Product 결과 생성이 Domain 제한 75초를 넘겨 timeout으로
    끝났고, HTTP 200의 5필드 응답에는 검색 근거 0개와 분석 시간 초과 안내가 반환됐다.
    요청한 비교 답변 생성은 실패했다.
  - 별도 제출 재생은 입력 9,068·출력 1,578토큰으로 15개 셀과 6개 인용 청크를 생성해
    구조 검증상 `complete`를 통과했다. 수작업 원문 대조에서는 최소 6/15개 셀에 명확한
    오류가 있었다. 모펀드 투자비율을 자펀드의 직접 투자비율로 옮긴 3개 셀,
    수수료 정보가 없는 청크를 인용한 2개 셀, 유동성 정보가 없는 청크를 인용한 1개 셀이다.
  - 개발 중 429 사용량 제한, 40009 Unsupported function, 미지원 `tool_choice=required`,
    제출 필드 누락도 관찰했다. `required`는 제거하고 지원되는 이름 지정·기본 선택을
    사용하며, 비교 셀은 모델 노출 schema에서 필수화했다.
- 결론: **답변 품질 채택 보류**. 상품 식별·문서별 검색·셀/참조 구조 검증은 구현됐지만,
  실제 API 완료와 사실의 주체·내용 검증은 통과하지 못했다. `coverage=complete`는 셀과
  참조의 형식적 완전성으로만 해석한다. 다음 검증은 불필요한 비교 항목 확장과 제출량,
  모·자펀드/클래스 구분, 항목별 인용 내용의 일치에 초점을 둔다. timeout이나 검색 상한만
  늘려 품질 문제가 해결됐다고 판단하지 않는다.
- 관련 PR/이슈: 없음. `codex/product-comparison` 브랜치의 검토용 구현.

## 2026-09-06 상품 비교 항목 상한 축소 검증

- 가설: 질문에 필요한 최소 항목을 선택하고 비교 항목 상한을 5개에서 3개로 강제하면
  요청하지 않은 비용·유동성 확장과 구조화 제출량을 줄일 수 있다.
- 방법: 조회·비교 Tool schema, 카탈로그 입력 검증, 검색 config와 최종 비교 계약을
  1~3개로 맞췄다. 선택 가능한 항목 5종은 유지하고 프롬프트는 단일 항목 요청 1개,
  안정성만 2개, 일반적인 차이와 안정성은 3개를 지시했다. 기존과 같은 3상품 질문을
  실제 HCX-007·Qdrant·FastAPI 경로에서 1회 실행했다. 개인 질문·추적은 제외 경로에 보존했다.
- 결과:
  - 실제 선택은 위험·원금보장 2개였고 6셀·6개 인용 근거를 제출했다. 비용·유동성은
    선택하지 않았다. 상품 식별은 정확했고 병렬 검색은 약 0.743초에 완료됐다.
  - HTTP 200·정확한 5필드로 42.051초에 최종 답변을 완료했다. 이전 최종 79.129초
    timeout과 달리 이번에는 완료됐지만 단일 실행 간 관찰이며 평균 성능 개선의 증거는 아니다.
  - 프롬프트가 요구한 투자전략 항목은 누락됐다. 원래 질문의 상품별 차이가 빠졌는데도
    `determined`와 `coverage=complete`로 제출했다.
  - 중장기·장기의 원금보장 셀은 관련 내용이 없는 연혁 청크를 인용했다. 최소 2/6셀의
    인용 오류이며 결론의 동일종목 투자한도 주장도 최종 근거 6개에서 확인되지 않았다.
    해당 한도는 검색 자료에는 있었지만 원문의 예외 조건도 생략했다.
- 결론: **상한 축소는 반영하되 답변 품질 채택은 계속 보류**. 코드가 강제하는 항목 개수,
  HCX의 의미상 필요한 항목 선택, 문장과 인용 내용의 일치는 별개의 검증 대상이다.
  이번 결과만으로 의미 오류가 해결됐거나 안정적인 완료율을 확보했다고 판단하지 않는다.
- 관련 결정: [최소 비교 항목](decisions/20260906-product-comparison-minimal-criteria.md).

## 2026-09-06 비교 Tool의 독립 답안 생성 평가

- 가설: `compare_products`가 상품별 검색과 비교 답안 생성을 함께 맡고, 작성 모델에는
  현재 질문·확정 대상·비교 항목·중복 제거한 원문만 전달하면 Product의 누적 대화와
  비교 작성 입력을 분리할 수 있다.
- 방법: 비교 셀 제출·검증·교정 경로를 제거하고 별도 HCX-007 비추론 작성 역할을
  연결했다. 기존과 같은 기간별 국공채 3상품 질문을 실제 FastAPI·HCX·Qdrant 경로에서
  1회 실행했다. 답안 정확성을 차단하는 런타임 검증기는 추가하지 않았다. 개인 질문과
  LangSmith trace는 Git 제외 경로에 보존했다.
- 결과:
  - HTTP 200·정확한 5필드, 전체 35.611초, Product 24.734초에 완료됐다. 카탈로그
    코드 교정 1회 후 3상품을 정확히 식별했고 투자전략·위험·원금보장 3항목을 선택했다.
  - Product 모델은 조회와 비교 호출까지 2회 사용했다. 비교 Tool 내부에서 병렬 검색
    약 0.812초, 작성 약 8.070초를 수행한 뒤 Product를 종료했다. 보완 검색이나 답안
    교정 없이 생성한 본문을 API까지 보존했다.
  - 작성 입력은 SystemMessage+HumanMessage 2개, 원문 15청크였다. provider 기준
    입력 6,520토큰·출력 332토큰, 메시지 본문 13,328자, 원문 본문 합계 7,337자였다.
    최종 인용 6청크만 `retrieved_context`에 포함했다.
  - 이전 작성 입력 9,451토큰과 달리 이번은 6,520토큰이지만 비교 항목, 검색 근거와
    프롬프트도 바뀌었다. 입력 분리만의 개선율이나 평균 지연 개선으로 해석하지 않는다.
  - 장기 상품의 위험등급이 입력과 최종 인용 모두에 있는데도 정보가 없다고 답했다.
    중장기의 위험등급·예금자보호·금리위험은 전체 입력에 있었으나 최종 인용에서 빠졌다.
    중장기 문서의 국내 채권 설명을 세 상품 공통의 국공채 특성으로 좁혀 일반화했다.
  - 제공된 비교지수 등 구체적인 전략 차이와 원금보장 여부의 설명이 부족했다.
    답안은 `determined`, 누락 조건·경고 빈 배열로 반환됐으며 새 경로는 이를 판정하거나
    고치지 않고 그대로 전달했다.
- 결론: **답안 생성 책임 이전과 컨텍스트 분리는 확인했으며, 답안 품질 채택은 보류**.
  위 내용은 개발 후 관찰 결과이며 런타임 검증 절차가 아니다. 단일 실행으로 품질 안정성이나
  완료율을 주장하지 않는다. 다음 개선은 비교 답안의 구체성과 실제 인용 선택에 집중한다.
